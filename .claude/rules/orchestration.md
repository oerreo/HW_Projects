# 오케스트레이션 규칙

## 계획 우선
- 작업 시작 전 프로젝트의 `docs/plan.md`의 현재 단계를 읽고, 이번에 할 일을 작은 sub job으로 나눈다.
- 각 sub job에는 입력(스펙/파일), 산출물, 통과 기준(어떤 시뮬레이션이 무엇과 일치해야 하는지)을 명시한다.
- 계획이 바뀌면 실행 전에 프로젝트의 `docs/plan.md`를 먼저 고친다.

## 모델 역할
| 역할 | 모델 | 수단 |
|---|---|---|
| 계획, 아키텍처 결정, 분배, 결과 검수 | Fable (메인 세션) | 직접 |
| sub job 실행: 모델/RTL/HLS/TB 작성, 시뮬레이션, 디버그, 조사 | Opus | `Agent(subagent_type: "hw-worker")` 또는 `model: "opus"` |
| 문서: 스펙 정리, 로그, Notion 정리, 논문 원고 | Sonnet | `Agent(subagent_type: "doc-writer")` 또는 `model: "sonnet"` |

- 기본 effort는 medium. 사용자가 따로 지시할 때만 바꾼다.
- 동시에 띄우는 agent는 최대 2개.
- Fable은 구현을 직접 하지 않는 것이 원칙이나, 몇 줄 수정이나 설정 파일처럼 위임 비용이 더 큰 일은 직접 한다.

## 수퍼바이저 검수
- agent의 "통과했다"는 보고를 그대로 믿지 않는다. 로그의 pass/fail 카운트, mismatch 수, 리포트 수치를 직접 확인한 뒤 완료로 처리한다.
- 측정하지 않은 수치(면적, Fmax, latency)를 문서나 논문에 쓰지 않는다. 추정치는 추정이라고 표시한다.
- 선행 연구 대비 주장(novelty, 성능 우위)은 출처가 확인된 것만 쓴다.

## 사용자 확인이 필요한 것
- DC 실행, GitHub push, 주제나 로드맵의 큰 방향 전환.
- 그 외에는 묻지 않고 진행하고, 결정 사항과 근거를 로그에 남긴다.
